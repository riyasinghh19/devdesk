The traps that catch everyone

  • MM vs mm in SQL Server. MM is month, mm is minutes. FORMAT(d, 'yyyy-mm-dd') gives "2026-05-31" for 31 October at 18:05.
  • MI vs MM in Snowflake and Postgres. Minutes are MI. Using HH24:MM prints the month in place of minutes.
  • Postgres pads names. TO_CHAR(d, 'Month') returns "October  " with trailing spaces. Add FM to trim: 'FMMonth'.
  • MySQL %M is the month name, not minutes. Minutes are %i.
  • Spark: YYYY is the week-based year. On 31 December it can show next year. Use lower-case yyyy.
  • SQL Server FORMAT is slow on large tables (it runs through .NET). For millions of rows, use CONVERT with a style number.

Frequently asked questions

How do I parse a text date instead of formatting one?

Use the same codes with the parsing function: Snowflake TO_DATE('31/10/2026', 'DD/MM/YYYY'), Postgres TO_DATE(...) the same way, SQL Server CONVERT(date, '31/10/2026', 103), MySQL STR_TO_DATE('31/10/2026', '%d/%m/%Y'), BigQuery PARSE_DATE('%d/%m/%Y', '31/10/2026').

Should I store dates as formatted text?

No. Store DATE or TIMESTAMP and format only when you display. Text dates sort wrongly ("10/02" before "9/30") and can't be compared or added to.

Which format should I use in reports for India?

DD/MM/YYYY or DD-Mon-YYYY (31-Oct-2026). The month name removes any doubt between Indian and US readers.
